# 需求规格

## 1. 目标

QQ Message Monitor 为陪伴型 Agent 提供稳定、低干扰、只读的 QQ 会话上下文。服务应在目标账号可用时自动采集，在账号离线时保持低资源休眠，并允许 Agent 高效了解新动态、读取会话和追溯摘要证据。

## 2. 第一版范围

### 2.1 消息来源

- 支持 Windows PC QQ。
- 使用独立运行的 LLOneBot 作为首个 Message Bridge，经 PMHQ 拉起主人日常使用的官方 QQ，GUI 保持可用；NapCat 保持 OneBot 11 协议兼容，第一版不验证。
- 使用 OneBot 11 正向 WebSocket 双工连接接收事件和调用查询接口。
- 以字符串形式的 `targetSelfUin` 作为目标账号唯一标识。
- 只有连接上报的 `self_id` 与 `targetSelfUin` 一致时才激活采集。

### 2.2 采集范围

- 群聊固定采用白名单，名单项为群号字符串。
- 好友支持 `all` 和 `whitelist` 两种模式。
- 私聊事件中 `sub_type` 非 `friend` 的群临时会话不属于好友采集范围，直接丢弃。
- 采集收到的消息和主人自己发送的消息。
- 保存 QQ 号作为稳定身份，保存消息发生时的昵称用于自然表达。
- 好友会话 ID 永远是对端好友 QQ 号；主人发出的好友消息也不把会话 ID 记成主人 QQ 号。
- 群成员名称优先使用消息事件中的群名片，其次使用昵称，最后回退到 QQ 号。
- 历史消息保存发生时的名称快照；后续改名不重写旧消息。
- 屏蔽名单外事件后再进入持久化和摘要链路。

### 2.3 消息内容

- 保存 OneBot 结构化消息段和可读 Message Projection。
- 第一版直接文本化文本和 `@`；表情在桥提供名称时文本化，否则与回复一样使用简洁占位符。
- 图片、语音、文件、卡片等保留结构化数据，并以描述性占位符进入 Message Projection。
- 第一版不包含 OCR、图片理解、语音转写和文件内容解析。
- 后续多媒体处理只能扩展 Message Projection，不改变消息身份和摘要单元边界。

### 2.4 本地持久化

- 使用单个本地 SQLite 数据库。
- 消息写入必须幂等，同一源消息重复到达时不得产生重复记录。
- 原始消息内容和摘要分别配置保留期。
- 原始内容过期后，允许保留 Summary-Only Unit。
- 所有时间使用 Unix epoch 毫秒，所有 QQ 标识使用字符串。

### 2.5 断线与缺口

- 首次成功连接建立 Monitoring Baseline，不导入此前聊天历史。
- 已建立基线后发生断线，第一版不执行历史补偿：重连时将断开区间直接记录为账号级 Capture Gap，并通过工具明确披露。
- 检查点随采集持续更新，用于界定缺口区间，并为未来的补偿扩展保留恢复起点。
- 历史补偿（调用桥的历史消息 API 回补缺口）是未来扩展；引入时必须复用既有消息幂等键，且不得改变已冻结单元边界。

### 2.6 撤回

- 以 OneBot `friend_recall` 和 `group_recall` 通知作为撤回事实来源。
- 根据会话和 `message_id` 标记 Recalled Message。
- 是否保留撤回原文、是否向 Agent 暴露原文由配置控制。
- 撤回不改变消息和摘要单元边界。
- 摘要前撤回的消息以占位符参与摘要；摘要后撤回只标记受影响单元，不级联重算后续摘要。

### 2.7 后台摘要

- 只有摘要群白名单中的群聊参与摘要；该名单必须是采集群白名单的子集。
- 好友会话不参与摘要，这是有意设计：私聊流量低、直读原文更准确，且一对一内容隐私敏感度最高；数据模型保留逐会话扩展能力，后续可加好友摘要白名单而无需改表。
- 同一会话未摘要消息数量达到 Summary Threshold 时创建后台任务。
- 任务真正开始时按单次调用 token 预算冻结最旧的一段未摘要消息（通常为全部）；之后到达的消息与超出预算的剩余消息属于后续单元。
- 每个 Summary Unit 恰好对应一次模型调用，不做单元内分块归并；积压超出预算时分批成串行的时间段单元。
- 同一会话摘要任务严格串行。
- 下一单元注入紧邻的前一成功摘要作为 Preceding Summary Context。
- 前一单元失败时，下一单元允许在无前序摘要的情况下继续。
- 失败任务在固定边界上重试；耗尽重试次数后形成 Summary Gap。
- 摘要模型由 MCP 独立调用，不依赖 Agent 当前会话。
- 摘要只输出消息可支持的事实，不进行长期关系或心理判断。

### 2.8 动态摘要维度

- `summaryText` 是固定的整体摘要文本，用于展示和后续摘要连续性。
- 其余 Summary Dimension 均由配置的字段名和描述定义。
- 每个维度返回零个或多个 Summary Finding。
- Summary Finding 由事实文本和支持它的源消息关联构成。
- 对 Agent 暴露短 Summary Reference，不要求 Agent填写 OneBot 消息 ID。
- 配置变更只影响之后创建的单元；旧单元保存 Summary Schema Snapshot，不自动重算。

### 2.9 Agent 进度

- Feed Progress 与 Conversation Read Progress 独立保存。
- `qq_feed_pull` 成功返回更新索引后推进 Feed Progress，不表示会话已读。
- 摘要完成本身是一种 Feed 更新，即使没有新增消息。
- 只有从当前未读起点连续读取时自动推进 Conversation Read Progress。
- 定点引用、最近内容和任意游标读取不自动推进。
- Agent 可显式将一个会话一键标记为已读；该操作只修改 MCP 本地进度，不修改 QQ 客户端状态。

### 2.10 MCP 工具

第一版固定提供三个工具：

1. `qq_monitor_status`
2. `qq_feed_pull`
3. `qq_read_conversation`

详细契约见 [mcp-tools.md](./mcp-tools.md)。

## 3. 非功能要求

### 3.1 正确性

- 白名单外消息不得写入正式消息表。
- 账号不匹配的连接不得激活采集。
- 同一源消息重复到达时结果必须幂等。
- 摘要单元不得重叠，单元边界冻结后不得吸收后续消息。
- 摘要引用只能解析到同一数据库内真实存在的记录。

### 3.2 性能

- 实时采集路径不得等待摘要模型。
- SQLite 使用 WAL、预编译语句和短事务。
- 摘要并发默认全局 1，同一会话始终为 1。
- 离线状态只保留 MCP、SQLite、清理调度和一个低频 WebSocket 重连定时器。
- 状态工具不得扫描完整消息表。
- 在实现和基准测试前不承诺具体内存、CPU 或延迟数值。

### 3.3 可靠性

- WebSocket 断开后自动重连。
- 本地连接除 socket 关闭外，还使用心跳超时识别半开状态。
- 消息落库、单元冻结和进度推进必须使用事务保证边界一致。
- 服务重启后能够恢复连接检查点、摘要队列和 Agent 进度。
- 捕获不完整时披露 Capture Gap，不将缺失伪装为空会话。
- 子系统故障必须以结构化 issue 通过状态工具披露，使用可直接转述给主人的自然语言消息；摘要单元失败同时作为 Feed 更新出现。

### 3.4 数据边界

- OneBot Token 和模型 API Key 只通过环境变量读取。
- 工具输出不包含 Token、API Key 或数据库绝对路径。
- 默认只连接 `127.0.0.1` 上的桥服务。
- QQ 侧只读；本项目不注册发送类 MCP 工具。
- 摘要将白名单群消息的投影发送给配置的模型服务；服务地址由用户配置，使用远程服务时消息内容离开本机。

### 3.5 可维护性

- Message Bridge 适配与领域逻辑隔离。
- OneBot 原始事件必须先标准化，再进入存储和摘要。
- 动态摘要维度不得要求数据库新增列。
- 配置和数据库必须有版本号及迁移入口。

## 4. 明确不在第一版范围

- 普通 QQ 进程的 UI Automation、通知抓取、缓存逆向或运行后注入。
- QQ 消息发送、撤回、点赞、群管理和好友管理。
- 移动端 QQ。
- 自动 hook、定时唤醒 Agent 或主动发起 Agent turn。
- OCR、ASR、多模态图片理解和文件正文提取。
- 首次启动时批量导入历史聊天。
- 断线或离线区间的历史补偿；第一版只记录 Capture Gap，不调用桥的历史消息 API。
- 批量重算旧摘要。
- Web 管理后台。
- 多个目标 QQ 账号同时写入同一服务实例。

## 5. 验收标准

| 编号 | 场景 | 通过条件 |
|---|---|---|
| AC-01 | 桥未运行（QQ 未经 LLOneBot 启动或已退出） | MCP 保持可调用，状态为休眠，已有数据可读 |
| AC-02 | 错误 QQ 账号连接 | 不写入消息，状态报告账号不匹配 |
| AC-03 | 目标账号连接 | 验证 `self_id` 后进入活动状态；非首次连接同时记录断开区间的 Capture Gap |
| AC-04 | 群白名单 | 只持久化名单内群消息 |
| AC-05 | 好友全部模式 | 任意好友新消息可入库 |
| AC-06 | 主人发言 | 消息入库且 `isOwner=true` |
| AC-07 | 重复事件 | 相同消息只存在一条记录 |
| AC-08 | 摘要冻结 | 任务开始后到达的消息进入下一单元 |
| AC-09 | 摘要连续性 | 下一成功任务获得前一成功摘要上下文 |
| AC-10 | 摘要完全失败 | 单元标记失败，后续单元继续运行 |
| AC-11 | 动态维度 | 新增配置字段无需改表即可出现在新摘要中 |
| AC-12 | 配置变更 | 旧摘要保持原 Schema，新摘要使用新 Schema |
| AC-13 | Feed 更新 | 摘要完成可在无新消息时单独出现 |
| AC-14 | 阅读进度 | Feed、连续阅读、定点查看互不误推进 |
| AC-15 | 一键已读 | 不返回正文即可推进单会话本地阅读进度 |
| AC-16 | 原文过期 | 摘要仍可读取，证据引用报告原文已过期 |
| AC-17 | 断线离线区间 | 工具可见 Capture Gap |
| AC-18 | QQ 侧只读 | 代码和 MCP 工具清单不存在发送类入口 |
| AC-19 | 故障披露 | 摘要模型不可用或单元失败时，状态工具返回 `degraded` 和可转述的结构化 issue，单元失败同时出现在 Feed |

## 6. 已知未验证事项

- LLOneBot `reportSelfMessage` 的实际行为（含主人从手机端发送后同步到 PC 的消息是否上报）需要在集成测试中确认。
- OneBot 不同事件中 `message_id` 的类型和作用域需要通过真实样本固定适配规则。
- TakiAgent 的 MCP 客户端已实现（`TAKI_DATA_DIR/mcp-servers.json` 扁平映射、启动时以 `shell:false` 拉起 stdio 子进程、工具命名空间化），但未经真实外部 MCP 服务端验证，需在接入阶段实测工具清单、Schema 与退出行为。
- 目标资源预算需要通过实现后的 Windows 基准测试确定。
